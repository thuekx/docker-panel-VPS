# Database access from outside and table tools (DB-02)

Status: IN PROGRESS, 2026-11-26. Roadmap slot 14d (RAYX-1 = A). Decision DB-2 open (recommended: a port per
website with an address list).

## Table tools (built)
- Database page: **Check tables**, **Repair tables**, **Optimize** for the ticked tables, or all of them.
- MariaDB: `CHECK TABLE`, `REPAIR TABLE`, `OPTIMIZE TABLE` over the client the console uses (Docker: inside the db
  container with its secret file; native: the host MariaDB over its socket). The table names come from the database's
  own list and are quoted (a backtick doubled), never taken as SQL. The answer is the database's own rows (status,
  note, info, warning, error); any error marks the run as not OK.
- PostgreSQL has no check or repair: only **Optimize**, as `VACUUM (ANALYZE)` on the whole database.
- Each run takes the change lock (no backup or restore at the same time), at most 5 minutes; the audit log names the
  operation, how many tables and whether errors came back.

## Access from outside (DB-2 = port per website, recommended)
Off by default. Per website: on/off and up to 20 addresses or networks (`0.0.0.0/0` and `::/0` refused).

- **A gate in the agent**, not a Docker published port. Docker's published ports pass by ufw and would need rules in
  the `DOCKER-USER` chain, which are missing after a reboot until the agent puts them back (a moment where the port is
  open to everyone). The agent instead listens on the website's port itself, checks the visitor's address against the
  list before reading a byte, and only then copies the bytes to the db container (the host reaches containers on the
  website's internal network; checked on Docker 29). If the agent is down, the port is closed.
- Ports: MariaDB from 33061, PostgreSQL from 54321, one per website, kept in `site.json`. The agent also adds a ufw
  rule per address (`allow from ADDR to any port P proto tcp`, comment `nostek db <id>`), so two filters must agree;
  the provider's security group has to open the port too (as for SFTP 2222).
- The account is the website's own database user and password (shown on the Database page as today), never root.
- TLS: MariaDB 11.4 and newer turns TLS on by itself with a generated certificate; the gate additionally refuses
  plain connections where it can tell (MariaDB `require_secure_transport` for users from outside the container
  network). PostgreSQL gets a self-signed certificate made by the agent and `ssl=on`, with `hostssl` required for
  addresses outside the container network.
- Native websites (host MariaDB): the same gate in front of the host's socket, user limited to the website's
  database.
- Audit: on, off and every list change; a refused address is counted (not logged per try).

## Tests (plan)
Table tools: refused op and table names, quoting, lock, PostgreSQL optimize only, answer parsing (built). Gate:
allowed and refused addresses (the refused one gets no byte), list limits, port allocation, ufw calls, closed when
off, survives a container IP change, no password in an answer or log.
