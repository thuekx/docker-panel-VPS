# Database access from outside and table tools (DB-02)

Status: BUILT v1.36.0, 2026-11-26. Roadmap slot 14d (RAYX-1 = A). Built on the recommended option of decision DB-2
(a port per website with an address list); the decision itself is still open.

## Table tools (built)
- Database page: **Check tables**, **Repair tables**, **Optimize** for the ticked tables, or all of them.
- MariaDB: `CHECK TABLE`, `REPAIR TABLE`, `OPTIMIZE TABLE` over the client the console uses (Docker: inside the db
  container with its secret file; native: the host MariaDB over its socket). The table names come from the database's
  own list and are quoted (a backtick doubled), never taken as SQL. The answer is the database's own rows (status,
  note, info, warning, error); any error marks the run as not OK.
- PostgreSQL has no check or repair: only **Optimize**, as `VACUUM (ANALYZE)` on the whole database.
- Each run takes the change lock (no backup or restore at the same time), at most 5 minutes; the audit log names the
  operation, how many tables and whether errors came back.

## Access from outside (DB-2 = port per website, recommended)
Off by default. Docker websites with a database only (the host MariaDB of native websites is shared). Per website:
up to 20 addresses or networks; anything wider than /8 (IPv4) or /16 (IPv6) is refused, so `0.0.0.0/0` and `::/0`
are too.

- **A gate in the agent**, not a Docker published port. Docker's published ports pass by ufw and would need rules in
  the `DOCKER-USER` chain, which are missing after a reboot until the agent puts them back (a moment where the port
  is open to everyone). The agent instead listens on the website's port itself and checks the visitor's address
  against the list before reading a byte. Only then does it join the visitor to the db container, whose address it
  looks up on each connection, so a recreated container is found again. The host reaches containers on the website's
  internal network; this was checked on Docker 29. If the agent is down, the port is closed.
- **TLS only.** The gate reads the visitor's first message and closes a plain one.
  - MariaDB: the answer to the server's greeting must carry `CLIENT_SSL`.
  - PostgreSQL: an `SSLRequest`, or a direct TLS ClientHello.
  - Checked with the pinned MariaDB 11.8 image: it makes its own certificate and serves TLSv1.3. Its default client
    connects through the gate, and `--skip-ssl` is closed.
  - PostgreSQL starts with `ssl=on` and a self-signed certificate the agent makes (`db-tls/`, key 0600, uid 999), but
    only while access is on. The website's own containers keep connecting as before.
- **Ports.** MariaDB from 33061, PostgreSQL from 54321, one per website, kept in `site.json` (`remote_db`). A list
  change keeps the port.
- **Firewall.** The agent also adds a ufw rule per address (`allow from ADDR to any port P proto tcp`, comment
  `nostek db <id>`), so two filters must agree. The provider's security group has to open the port too (as for SFTP
  2222).
- **Account.** The website's own database user and password, never root.
- **Lifecycle.**
  - Job `remote-db`: settings (PostgreSQL restarts its database), firewall, gate.
  - Moving a website to the trash closes its port and removes its rules; a restore opens them again.
  - At agent start, the rules are put back and the gates opened. After a server restore, this happens at the next
    start.
- **Audit.** On, off and every list change. Refused addresses and plain visitors are counted, not logged per try.
  The counts are shown on the card.

## Tests
Table tools: refused op and table names, quoting, lock, PostgreSQL optimize only, answer parsing (built). Gate:
address list checks; a refused address gets no byte; a plain visitor is closed after the greeting; a TLS visitor is
joined; list change keeps the port and changes the ufw rules; trash and restore; off closes the port; PostgreSQL
SSLRequest check; compose TLS lines. A real-MariaDB run (`NOSTEK_REAL_DB`, skipped in CI) checked TLS through the
gate and the refusal of `--skip-ssl`.
