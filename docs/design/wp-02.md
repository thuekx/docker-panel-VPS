# WP-02: WordPress Tools wave 2 (v1.51.0, v1.52.0)

Roadmap 15k. Follows WP-01 (WordPress Tools, v1.6.0) and BAK-01 (backups, v1.7.0).
Status: LIVE 2026-11-28 02:07 WIB (v1.51.0 safe update, v1.52.0 staging copy), installed from Settings → Update.

## Wave 1: safe update (v1.51.0)
Every update from the WordPress page (WordPress core, "update everything", one plugin or theme, all plugins or
all themes) now runs as a job:

1. **Check before**: `wp eval` loads WordPress with its plugins and theme and asks the front page through
   WordPress's own HTTP client (`wp_remote_get(home_url("/"))`). A PHP fatal error in a plugin or theme shows here
   as WordPress not loading; the front page's HTTP status is noted too.
2. **Backup** "before-update" (BAK-01: database and files; the last 3 are kept), shown on the Backups page.
3. **Update** with WP-CLI (15 minutes at most).
4. **Check after**, the same check.
5. **Put back** when the update broke a website that worked: WordPress loaded before and does not now, or the
   front page answered below 400 before and answers 500 or more now. The backup is restored (database and files)
   and the job ends as failed with what broke. A website that was already broken before is updated but never put
   back on that ground.
6. Otherwise the job is done and names its backup; a failed update that left the website working says so and names
   the backup too.

The page shows the steps live (the job card at the top of the WordPress page), and the change lock of the website
keeps a second change out while it runs. The agent API takes `"safe": true` on `POST …/wp/core`,
`…/wp/plugins` and `…/wp/themes` (update only) and answers 202 with the job; without it the old quick update stays
for scripts. The panel sends `safe` for every update unless a form says `safe=0`.

When the server cannot reach its own website over HTTPS (a name that does not point here yet), the front page check
reads "no answer" both times: the fatal-error check still works, and an error 500 is then not seen.

## Wave 2: staging copy (v1.52.0)
- **Make a staging copy** (WordPress page → Staging copy): a new WordPress website `staging.<domain>` (id
  `staging-<id>`, reached on its preview address `staging-<id>.<preview zone>` until a DNS record points the name
  here), made like any other website with the same engine, web server and PHP. One job (kind `staging`) creates it
  and then copies the live website into it through the MIG-01 import core:
  - the files as they are now (caches, the agent's own partial uploads and the live `wp-config.php` are left out:
    the copy keeps its own `wp-config.php` with its own database login),
  - a consistent dump of the live database, loaded into the copy's own database,
  - the table prefix carried, the addresses rewritten to the copy's address (`wp search-replace`), caches cleared,
    and a check that the copy loads with an administrator.
  - Search engines are told to stay away from the copy (`blog_public` 0). Accounts are the same as on live.
- One copy per website; a staging website has no copy of its own. Its record says whose copy it is
  (`staging_of`), and both WordPress pages link to each other.
- **Push to live** (on either page, after a confirmation): the same import the other way (job kind `push` on the
  live website), after a before-migrate backup of the live website (Backups, the last 3 kept). The live website
  keeps its own address and its own search-engine setting. Changes made on live since the copy was made (orders,
  comments) are replaced too: the page says so before the push.
- **Start over**: delete the copy like any website (Website → Delete) and make a new one.
- Agent API: `POST /v1/sites/{id}/staging` (202 with the job and the new website), `POST
  /v1/sites/{id}/staging/push` with `{"from": "<staging id>"}` (202 with the job); a push is refused unless `from`
  is the staging copy of `id`.

## Tests
- Agent: healthy update (backup made, no restore), fatal error after the update (files put back), error 500
  after, already broken before (not put back), update failed but the website works, refusals (other actions,
  names, unknown website, busy, no backup made), `brokeBy` table; API: 202 job and refusals.
- Panel: updates go to the agent as safe jobs, the job card in both languages for running, done, put back and
  failed, jobs of another kind or website are not shown, the progress poll knows the steps.
- Harness (real WordPress): a safe update of all plugins is done with a before-update backup; a harness plugin
  that breaks WordPress after any `wp plugin update` is put back by itself and the website answers 200 again.
- Staging (agent): copy made with its record, files, its own wp-config.php, no caches or partial uploads, addresses
  rewritten, search engines off; a second copy and a copy of a copy refused; push with a live backup first, files
  live, search setting of live kept; pushes from a website that is not the copy refused; busy. Panel: the card in
  each state (none, has a copy, is a copy) in both languages, make, push (confirm, names checked), the push job
  card and the staging job page. Harness (real WordPress): copy made and answering on its address with search
  engines off and its own database login, second copy refused, push to live keeps live's address, backup made,
  copy deleted.
- Mutants: no backup, no put back, error 500 not seen, failed update reported as done; live database login copied
  into the copy, copy open to search engines, push leaves live hidden from search engines, any website pushed over
  live.
